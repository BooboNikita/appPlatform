# 动态配置「配置项 + 灰度下发」改造方案

## 一、Summary（目标）

把现有「整包 JSON 存 MinIO 文件」的动态配置方案，改为「拆解为配置项存数据库 + 按用户名灰度下发」：

1. 新建配置项表 `dynamic_config_item`，以 **版本范围 / 环境 / 所属域 / 配置项 key** 为维度存储每个配置项。
2. 新建灰度名单表 `dynamic_config_item_gray_user`，每个配置项支持独立的白名单 / 黑名单；结合百分比灰度设计确定性的分桶算法。
3. **两级历史与回溯**：整包快照（`dynamic_config_history`）+ 配置项级历史（`dynamic_config_item_history`），既支持批量发布的版本回溯，也支持单个配置项独立回溯而不影响其他项。
4. 对外接口 **JSON 形态保持不变**：上传仍是整包 JSON（服务端内部拆解入库），下发仍是拼接好的 JSON（拼接后做格式校验再返回）。
5. 前端管理平台动态配置页改为 **扁平配置项列表**，可逐项修改灰度配置，提供独立的名单管理弹窗、配置项历史弹窗与只读的下发 JSON 预览。

已确认决策（来自用户）：
- `/match` **新增可选 `username` 请求参数**（不传时按“非灰度”处理，兼容旧调用方）。
- **彻底放弃 MinIO 文件存储**，改为纯数据库存储。
- 前端为 **完全扁平的配置项列表**（去掉“配置文件”左右分栏布局）。
- 白名单/黑名单 **单独建表**，前端用 **独立名单管理弹窗** 编辑。
- 回溯 **增加配置项级历史**，支持单项回溯。

## 三、数据模型设计

### 3.1 新增：`dynamic_config_item`（配置项表）

新建文件 `appPlatform/src/main/resources/sql/dynamic_config_item_table.sql`：

```sql
use app_platform;

CREATE TABLE IF NOT EXISTS `dynamic_config_item` (
  `id`           bigint       NOT NULL AUTO_INCREMENT COMMENT '主键ID',
  `config_id`    bigint       NOT NULL COMMENT '所属配置ID(dynamic_config.id)',
  `version_range`varchar(100) NOT NULL COMMENT '版本范围，如 1.0.0-2.0.0 / 1.5.0 / *',
  `env`          varchar(50)  NOT NULL DEFAULT 'prod' COMMENT '环境：prod(生产)/test(测试)',
  `domain`       varchar(100) NOT NULL COMMENT '所属域，如 homepage/detail/global',
  `item_key`     varchar(200) NOT NULL COMMENT '配置项 key，如 ai_entry',
  `item_value`   text         NOT NULL COMMENT '配置项值(JSON 序列化文本，保留原始类型)',
  `value_type`   varchar(20)  NOT NULL COMMENT '值类型：BOOLEAN/NUMBER/STRING/JSON',
  `enabled`      tinyint      NOT NULL DEFAULT 1 COMMENT '是否启用：1启用(下发)，0停用(不下发)',
  `gray_enabled` tinyint      NOT NULL DEFAULT 0 COMMENT '是否开启灰度：1开启，0关闭(全量下发)',
  `gray_percent` int          NOT NULL DEFAULT 0 COMMENT '灰度百分比 0-100',
  `remark`       varchar(500) DEFAULT NULL COMMENT '备注',
  `create_time`  datetime     NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
  `update_time`  datetime     NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '更新时间',
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_config_domain_key` (`config_id`,`domain`,`item_key`),
  KEY `idx_env` (`env`),
  KEY `idx_version_range` (`version_range`),
  KEY `idx_domain` (`domain`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='动态配置项表';
```

说明：
- `version_range` / `env` 从所属配置**冗余**存储，使扁平列表与灰度查询无需 JOIN，也满足「按版本范围、环境、域建表」的要求。
- 唯一键 `(config_id, domain, item_key)` 保证同一份配置内一个域下 key 不重复。
- `item_value` 存 JSON 序列化文本（`true` / `10` / `"str"` / `"[...]"` / `{...}`），拼装时反序列化即可还原原类型。
- **白/黑名单不在此表**，见 3.2。

### 3.2 新增：`dynamic_config_item_gray_user`（灰度名单表）

```sql
use app_platform;

CREATE TABLE IF NOT EXISTS `dynamic_config_item_gray_user` (
  `id`          bigint       NOT NULL AUTO_INCREMENT COMMENT '主键ID',
  `item_id`     bigint       NOT NULL COMMENT '配置项ID(dynamic_config_item.id)',
  `list_type`   varchar(10)  NOT NULL COMMENT '名单类型：WHITE(白名单)/BLACK(黑名单)',
  `username`    varchar(100) NOT NULL COMMENT '用户名',
  `operator`    varchar(100) NOT NULL DEFAULT 'system' COMMENT '操作人',
  `create_time` datetime     NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
  `update_time` datetime     NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '更新时间',
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_item_type_user` (`item_id`,`list_type`,`username`),
  KEY `idx_item_type` (`item_id`,`list_type`),
  KEY `idx_username` (`username`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='动态配置项灰度名单表';
```

设计理由：
- `UNIQUE(item_id, list_type, username)` **天然防重**，批量导入可幂等（`INSERT IGNORE` / 捕获重复键跳过）。
- `idx_username` 支持「反查某用户命中了哪些配置项」，便于排查问题。
- `operator` + `create_time` 提供审计能力。
- 支持分页、按用户名搜索、单条删除、按类型清空——前端可渲染为真正的表格。
- 配置项删除时**级联删除**其名单（应用层显式删除，表间不建外键，与项目现状一致）。

### 3.3 新增：`dynamic_config_item_history`（配置项级历史表）

```sql
use app_platform;

CREATE TABLE IF NOT EXISTS `dynamic_config_item_history` (
  `id`              bigint       NOT NULL AUTO_INCREMENT COMMENT '主键ID',
  `config_id`       bigint       NOT NULL COMMENT '所属配置ID(dynamic_config.id)',
  `domain`          varchar(100) NOT NULL COMMENT '所属域',
  `item_key`        varchar(200) NOT NULL COMMENT '配置项 key',
  `version_range`   varchar(100) NOT NULL COMMENT '版本范围(冗余，便于展示)',
  `env`             varchar(50)  NOT NULL COMMENT '环境(冗余，便于展示)',
  `item_value`      text         NOT NULL COMMENT '本次变更后的值(JSON 序列化文本)',
  `value_type`      varchar(20)  NOT NULL COMMENT '值类型：BOOLEAN/NUMBER/STRING/JSON',
  `enabled`         tinyint      NOT NULL DEFAULT 1 COMMENT '本次变更后是否启用',
  `gray_enabled`    tinyint      NOT NULL DEFAULT 0 COMMENT '本次变更后是否开启灰度',
  `gray_percent`    int          NOT NULL DEFAULT 0 COMMENT '本次变更后的灰度百分比',
  `gray_users_json` text         COMMENT '名单快照 JSON 数组，如 [{"listType":"WHITE","username":"u1"}]',
  `remark`          varchar(500) DEFAULT NULL COMMENT '备注',
  `operation_type`  varchar(20)  NOT NULL COMMENT '操作类型：CREATE/UPDATE/DELETE/REVERT',
  `operator`        varchar(100) NOT NULL DEFAULT 'system' COMMENT '操作人',
  `create_time`     datetime     NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
  PRIMARY KEY (`id`),
  KEY `idx_config_domain_key` (`config_id`,`domain`,`item_key`),
  KEY `idx_create_time` (`create_time`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='动态配置项历史表';
```

两个关键设计取舍：

- **不用 `item_id` 作为关联键**，而用业务键 `(config_id, domain, item_key)`。原因：整包回溯是「删旧插新」，`dynamic_config_item.id` 会重新生成；只有业务键才能在回溯后依旧连续、不丢历史。
- **记录变更「后」的状态**，所以「最新一条历史 == 当前值」，语义直观；单项回溯只需把某条历史的快照字段整体写回该配置项即可，不必反推。
- 名单以 `gray_users_json` 快照形式内嵌，保证单项回溯能完整还原当时的白/黑名单（名单表本身只存当前值）。

### 3.5 变更：`dynamic_config_history`（文件地址 → 整包快照 JSON）

编辑 `appPlatform/src/main/resources/sql/dynamic_config_history_table.sql`：

```sql
ALTER TABLE dynamic_config_history DROP COLUMN file_url;
ALTER TABLE dynamic_config_history ADD COLUMN snapshot_json LONGTEXT COMMENT '整包快照(含 items 与灰度名单的完整 JSON)';
```

`snapshot_json` 结构：

```json
{
  "metadata": { "versionRange": "...", "env": "...", "remark": "...", "publishTime": "..." },
  "configs":  { "域": { "配置项": 值 } },
  "items": [
    {
      "domain": "homepage", "itemKey": "ai_entry",
      "itemValue": "true", "valueType": "BOOLEAN",
      "enabled": 1, "grayEnabled": 0, "grayPercent": 0, "remark": "",
      "grayUsers": [ { "listType": "WHITE", "username": "u1" } ]
    }
  ]
}
```

- `metadata` + `configs` 供前端历史抽屉展示（`ConfigHistoryDrawer.vue` 直接读这两个字段，无需改动）。
- `items`（含内嵌 `grayUsers`）供「整包回溯」精确恢复配置项与灰度配置。
- **语义变更**：本表记录的是操作**完成后**的状态（不再是变更前）。好处是最新一条快照即为当前状态，且修复了原实现「UPDATE 记录的是变更前状态、最新状态永远缺失」的问题。唯一例外是 `deleteConfig`，因为删除后无内容可存，故写入删除**前**的状态作为留档。

## 四、灰度算法设计

新增 `appPlatform/src/main/java/com/app/appplatform/util/GrayReleaseUtil.java`。

### 4.1 判定规则（优先级从高到低）

```
isReleased(item, whiteSet, blackSet, username):
  1. item.enabled == 0                      → false   // 停用，永不下发
  2. item.grayEnabled == 0                  → true    // 未开灰度，全量下发
  3. blackSet 命中 username                 → false   // 黑名单最优先，即使命中也剔除
  4. whiteSet 命中 username                 → true    // 白名单次之，一定下发
  5. username 为空                          → false   // 无法判断身份，灰度项不下发
  6. bucket(seed, username) < gray_percent  → true/false // 百分比灰度
```

设计取舍：
- **黑名单 > 白名单**，保证“紧急剔除某个用户”不会被白名单覆盖。
- 未传 `username` 时灰度项**不下发**（若已全量放开，直接关闭灰度开关走全量，语义更清晰）。
- 名单来自 3.2 的独立表；下发时按 `config_id` **一次性批量查出**该配置全部配置项的名单，在内存中按 `itemId` 分组为 `whiteSet` / `blackSet`，**不产生 N+1 查询**。
- 用户名**区分大小写精确匹配**；写入时 `trim`，空串忽略。

### 4.2 分桶算法（确定性、稳定）

```java
seed   = domain + "." + itemKey;              // 每个配置项独立分桶 → 不同功能命中人群错开
digest = MD5(seed + "|" + username);          // 16 字节
v      = 取 digest 前 4 字节组成 int
bucket = Math.floorMod(v, 100);               // 0-99
命中   = bucket < grayPercent;                // 例：percent=10 → 约 10% 用户命中
```

- 用 MD5 而非 `String.hashCode()`，避免相邻用户名（user001、user002）分布不均。
- 以 `domain.itemKey` 作为 seed，保证「同一用户在不同配置项上命中结果不同」，避免灰度人群完全重叠。
- 同一用户 + 同一配置项的结果**恒定**，不会因重启/多实例而变化（无状态、可水平扩展）。

### 5.12 编辑 `service/impl/DynamicConfigServiceImpl.java`（核心）

移除 `MinioService` 依赖与全部文件读写逻辑，改为数据库实现。

**（a）历史快照的写入时机（关键约定）**

| 操作 | 整包快照 `dynamic_config_history` | 配置项历史 `dynamic_config_item_history` |
|---|---|---|
| `upload` 新建该 `(env, version_range)` | `CREATE`（写入后） | 每个配置项一条 `CREATE` |
| `upload` 覆盖同一 `(env, version_range)` | `UPDATE`（写入后） | 值/启用/灰度/百分比/备注**确实发生变化**的项各一条 `UPDATE`；被移除的项各一条 `DELETE` |
| `updateConfig` 元数据变更 | `UPDATE`（写入后） | 无 |
| `updateItem`（单项 PUT） | 不写（避免整包历史噪音） | 该配置项一条 `UPDATE` |
| `addGrayUsers` / `deleteGrayUser` / `clearGrayUsers` | 不写 | 该配置项一条 `UPDATE`（记录名单变化后的状态） |
| `deleteItem` | 不写 | 该配置项一条 `DELETE`（保留最后状态，便于恢复） |
| `revertItemToHistory`（单项回溯） | 不写 | 该配置项一条 `REVERT` |
| `deleteConfig` | `DELETE`（删除**前**状态，留档） | 各配置项一条 `DELETE` |
| `revertToHistory`（整包回溯） | `REVERT`（写入后） | 各项各一条 `REVERT` |

统一辅助方法：

- `saveHistory(DynamicConfig config, String operationType, String operator)` — 生成 3.5 结构的整包快照（含 `items` 与内嵌 `grayUsers`）。
- `saveItemHistory(DynamicConfigItem item, String operationType, String operator)` — 生成一条配置项历史：先 `grayUserMapper.findByItemId(itemId)` 查全部名单 → 序列化为 `gray_users_json`；`itemValue` 直接取当前值。**写入前用 `findLatestByConfigIdAndKey` 比对，内容完全一致则跳过**（避免重复写入）。

**（b）`uploadConfig(file, versionRange, env, remark)`**
1. 读取 `MultipartFile` 文本 → `JsonUtil.toObject(text, Object.class)` 解析为 `Map`。
2. 提取配置内容：若存在 `configs` 字段则取 `configs`，否则取整个对象（兼容前端旧结构）。
3. **格式校验**：内容必须为「域 → 配置项」两层结构，即每个顶层 value 必须是 JSON 对象；不满足则抛 `RuntimeException("配置内容格式错误：必须为 { 域: { 配置项: 值 } } 两层结构")`。内层值允许布尔/数字/字符串/对象/数组。
4. 按 `(env, versionRange)` 查 `findByEnvAndVersionRange`：
   - 存在 → 沿用该 `config_id`，更新 remark/update_time。
   - 不存在 → `insert` 新 `dynamic_config`。
5. 遍历配置项，按 `(config_id, domain, itemKey)` **UPSERT**：已存在则只更新 `item_value` / `value_type`，**保留原灰度开关、百分比与名单**（避免重新发布丢失灰度）；不存在则插入（默认 `enabled=1, gray_enabled=0, gray_percent=0`）。对每个**内容确实变化**的项写一条 `UPDATE` 历史（新增项写 `CREATE`）。
6. 删除本次未出现的旧 key：先查出待删 itemId → `deleteByItemIds` 级联清名单 → 删除配置项 → 逐条写 `DELETE` 历史。
7. 写整包快照（`CREATE` 或 `UPDATE`）。
8. 返回 `DynamicConfig`（输出结构不变）。

> 校验通过后再落库，满足需求中「验证格式后再返回」。

**（c）`updateConfig(id, file, versionRange, env, remark)`**
- 若 `versionRange`/`env` 变更，检查目标 `(env, version_range)` 是否已被其他 id 占用，冲突则抛「该版本范围与环境已存在配置」；否则调用 `updateMetaByConfigId` 同步配置项的冗余字段。
- 若传了 file → 复用（b）的解析与 UPSERT 逻辑（保留灰度配置），不再上传 MinIO。
- 写整包快照（`UPDATE`）。

**（d）`getConfigContent(id, env)`（管理端，全量）**
- 按 `configId` 查配置项，**不做灰度过滤、忽略 `enabled`**，拼装为 `{metadata, configs}` 返回。
- 拼装后做格式校验：`JsonUtil.toJson(obj)` 后再 `JsonUtil.toObject(json, Object.class)`，失败则抛异常。
- `metadata` 结构保持 `{configId, versionRange, publishTime, env, remark}`（与前端现有读取逻辑一致）。

**（e）`matchConfigContent(version, env, username)`（客户端下发）**
1. `findByEnv(env)` → `VersionUtil.isMatch(version, versionRange)` 过滤 → 取第一条（最新）。
2. 未匹配到返回 `null`（Controller 返回 404，与现状一致）。
3. 加载该配置的全部配置项；**一次性** `grayUserMapper.findByItemIds(...)` 查出全部名单，按 `itemId` + `listType` 分组为 `whiteSet` / `blackSet`。
4. 逐项 `GrayReleaseUtil.isReleased(item, whiteSet, blackSet, username)` 过滤。
5. 按域分组成 `LinkedHashMap<String, LinkedHashMap<String,Object>>`，**丢弃过滤后为空的域**。
6. 拼装 `{metadata: {...}, configs: {...}}` 并做格式校验后返回。
7. 全被灰度过滤掉时返回 `configs: {}`（保持输出结构不变，客户端按缺省逻辑处理）。

**（f）配置项级历史与回溯**

`getItemHistory(itemId)`：先 `findById` 拿到 `(configId, domain, itemKey)`，再按业务键查该配置项的变更历史（时间倒序）。

`revertItemToHistory(itemId, historyId, operator)`：
1. 校验 `history` 的 `(configId, domain, itemKey)` 与当前配置项一致（防止串项）。
2. 写当前状态的一条 `REVERT` 前快照？——**不需要**：因为历史表记录的是变更后状态，当前状态本身已是历史里的一条，直接覆盖即可，且覆盖动作会再写一条 `REVERT`，所以操作可逆。
3. 把历史的 `itemValue` / `valueType` / `enabled` / `grayEnabled` / `grayPercent` / `remark` 写回 `dynamic_config_item`（`update`）。
4. 名单还原：`deleteByItemId(itemId)` 清空当前名单 → 解析 `gray_users_json` → 逐条 `insert`。
5. 写一条该配置项的 `REVERT` 历史（状态与所回溯到的历史一致）。
6. 返回更新后的 `DynamicConfigItem`。

> 单项回溯**只影响该配置项**，同一个配置下其他配置项的值与灰度配置完全不受影响——这正是引入配置项级历史的目的。

**（g）整包历史与回溯**

- `getHistoryContent(historyId)`：解析 `snapshot_json` 返回（前端读 `metadata` / `configs`，`items` 冗余无害）。若 `snapshot_json` 为空（迁移前的旧记录），抛 `RuntimeException("该历史版本为旧版文件存储，不支持查看与回溯")`，**不能静默返回空**。
- `revertToHistory(configId, historyId, operator)`（整包，语义为「把整份配置回滚到某次发布的版本」）：
  1. 解析快照的 `items` 与内嵌 `grayUsers`。
  2. `deleteByConfigId(configId)` 删掉该配置下全部配置项 → `deleteByItemIds(...)` 级联删名单。
  3. 按 `items` 逐条 `insert` 配置项（**id 会重新生成**）→ 按 `grayUsers` 逐条 `insert` 到新 itemId 上。
  4. 同步 `dynamic_config` 的 `version_range` / `env` / `remark` / `update_time`。
  5. 写整包 `REVERT` 快照 + 各项 `REVERT` 历史（业务键关联，回溯后仍连续）。
  6. 返回 `DynamicConfig`。

> 整包回溯会覆盖该配置下**全部**配置项（这是它的设计语义，前端会明确提示）；只想改一项时使用单项回溯。

**（h）级联一致性**
- `deleteItem(id)`：先 `deleteByItemId` 删名单，再删配置项，最后写 `DELETE` 历史。
- `deleteConfig(id)`：删除全部配置项前先 `deleteByItemIds` 删名单；写整包 `DELETE` 快照与各项 `DELETE` 历史后再 `deleteByConfigId` 清理历史；不再有 MinIO 文件删除逻辑。

## 七、Assumptions & Decisions

1. `/match` 的 `username` 为**可选**参数；不传时灰度项不下发，非灰度项照常全量下发（保证旧客户端行为基本不变，只是新增的灰度项对旧调用方不可见）。
2. `(env, version_range)` 唯一：上传同一环境+版本范围视为**更新同一份配置**（保留各配置项已有灰度开关、百分比与名单），不再产生重复批次。
3. **白/黑名单独立建表**，通过独立接口增删改查；配置项的 `PUT /item/{id}` 不再承载名单，杜绝两套写入口。
4. 灰度优先级：**停用 > 黑名单 > 白名单 > 百分比**；未传 username 时灰度项不下发。
5. 分桶 seed 为 `domain.itemKey`，保证不同配置项灰度人群错开；结果确定性、无状态。
6. 下发拼装时**丢弃被过滤为空的域**；若全部过滤则返回 `configs: {}`，接口结构不变。
7. 上传 JSON 需满足 `{ 域: { 配置项: 值 } }` 两层结构；兼容带 `metadata`/`configs` 包装的旧格式（取 `configs`）。不满足则明确报错，不落库。
8. 前端扁平列表**不提供「新增单个配置项」**入口：新增/批量变更通过「上传JSON（整包拆解）」完成，避免重复实现两条写入路径。单条仅支持编辑、历史、删除，名单在弹窗内增删。
9. **两级历史**：整包快照用于批量发布的版本管理（回溯会覆盖该配置下全部配置项，前端明确提示）；配置项级历史用于单项回溯，互不影响。两表均记录**变更后**状态，因此「最新一条 == 当前状态」。
10. 配置项级历史以业务键 `(config_id, domain, item_key)` 关联，**不使用自发 id**，保证整包回溯（删旧插新）后历史仍连续。
11. 名单以快照形式内嵌在配置项历史中（`gray_users_json`），保证单项回溯能完整还原当时的白/黑名单。
12. 迁移前的历史记录（`snapshot_json` 为 `NULL`）无法查看与回溯，接口需返回明确错误，不静默返回空。
13. 表间不建数据库外键，级联删除在应用层显式完成，与项目现有风格一致。
14. 存量库中 `dynamic_config.file_url` 指向的 MinIO 文件在迁移后不再被引用（保留文件本身不做清理）。

   - `PUT /api-dynamic-config/item/{id}` / `DELETE /api-dynamic-config/item/{id}`（删除后其名单被级联清除，并写入 `DELETE` 历史）生效。
   - `GET /api-dynamic-config/gray-user/by-username?username=u1` 能反查到对应配置项。
4. 反向路径：上传非两层结构 JSON（如 `{"a": 1}`）→ 返回明确格式错误，且库中无脏数据（`dynamic_config`、`dynamic_config_item`、历史表均无残留）。

   - 整包历史抽屉：可查看并整包回溯。
